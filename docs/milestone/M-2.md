# M2 — Visual Representation & Embedding Pipeline

Now we move from **“Do we have valid sequential data?”** to:

> **How do we convert each observation into a representation that allows us to study temporal information without confounding the experiment with a complicated vision model?**

This milestone is deliberately **not** about building the GRU yet.

Our goal is to create a clean, deterministic pipeline:

```text
Raw sequence
     ↓
Frame sampling
     ↓
Image preprocessing
     ↓
Frozen pretrained visual encoder
     ↓
Frame embeddings
     ↓
Validation + caching
     ↓
Temporal analysis
```

The assessment asks for pretrained visual representations, embedding analysis, and investigation of how representations evolve over time. Take-Home Assessment

---

# M2.0 — What are we trying to achieve?

At the end of M2, given:

```text
sequence_001
```

we should be able to produce:

```text
E₁, E₂, E₃, ..., Eₙ
```

where each:

\[
E_t \in \mathbb{R}^{D}
\]

and therefore the complete sequence becomes:

\[
E = [E_1,E_2,\ldots,E_N]
\]

with shape:

\[
[N,D]
\]

For example, conceptually:

```text
Video
 │
 ├── Frame 1 ──→ DINOv2 ──→ [768]
 ├── Frame 2 ──→ DINOv2 ──→ [768]
 ├── Frame 3 ──→ DINOv2 ──→ [768]
 └── Frame N ──→ DINOv2 ──→ [768]
                             
                         [N × 768]
```

That matrix becomes the input to M3.

# M2.2 — Frame sampling

This is one of the easiest places to accidentally introduce experimental problems.

Suppose the original sequence contains:

```text
F1 F2 F3 F4 F5 F6 F7 F8 F9 F10
```

We might want:

```text
F1 F3 F5 F7 F9
```

or:

```text
F2 F4 F6 F8 F10
```

The sampling strategy itself can affect what temporal information the model sees.

Therefore define it explicitly.

---

## Initial strategy: uniform sampling

If a sequence contains \(L\) frames and we want \(N\) observations, select approximately uniformly:

\[
i_k =
\left\lfloor
\frac{k(L-1)}{N-1}
\right\rfloor
\]

for:

\[
k=0,\ldots,N-1
\]

Conceptually:

```text
Original

F1 F2 F3 F4 F5 F6 F7 F8 F9 F10 F11 F12

Uniform 4-frame sampling

F1 -------- F5 -------- F8 -------- F12
```

This is a good initial strategy because it avoids systematically favoring the beginning or end of the sequence.

---

# M2.3 — Important sampling rule

Don't randomly sample different frames every time we evaluate the test set.

That would introduce unnecessary variance.

For the initial controlled experiments:

```text
TRAIN
→ sampling can have controlled randomness if required

VALIDATION
→ deterministic

TEST
→ deterministic
```

For example:

```text
test sequence 001
→ always produces frames [1, 8, 15, 22]
```

This makes:

```text
baseline
vs
GRU
vs
shuffled
vs
corrupted
```

comparable.

---

# M2.4 — Image preprocessing

The preprocessing pipeline should be identical across all models.

Conceptually:

```text
Image
 ↓
RGB conversion
 ↓
Resize
 ↓
Center crop / encoder-specific transform
 ↓
Normalize
 ↓
Tensor
```

The exact normalization and image dimensions should come from the chosen pretrained encoder's official preprocessing configuration.

Do not invent preprocessing parameters simply because they are common elsewhere.

---

# M2.5 — Vision encoder

For the initial implementation, I would use a **pretrained frozen visual encoder**, consistent with the assessment.

DINOv2 is a strong candidate because it gives us image representations without requiring us to train the vision component ourselves.

The critical point isn't:

> “DINOv2 is the best vision model.”

It is:

> **“We need a stable visual representation so that the primary experimental variable is temporal modeling.”**

---

# M2.6 — Why freeze the encoder?

Imagine we compare:

```text
Model A

Image
 ↓
DINOv2
 ↓
Classifier
```

against:

```text
Model B

Image
 ↓
DINOv2
 ↓
GRU
 ↓
Classifier
```

If DINOv2 is frozen in both:

```text
             SAME
              │
              ▼
        Visual representation
              │
       ┌──────┴──────┐
       ↓             ↓
   Baseline         GRU
```

Then the primary difference is temporal processing.

But if we fine-tune DINOv2 only for the temporal model:

```text
Baseline → frozen DINOv2

Temporal → fine-tuned DINOv2
```

we cannot confidently attribute an improvement to temporal modeling.

That's a major experimental confound.

# M2.7 — Embedding extraction

Create something conceptually like:

```text
src/
└── embeddings/
    ├── extractor.py
    ├── cache.py
    └── validate.py
```

The extractor should:

1. Load the encoder.
2. Load one sequence.
3. Apply deterministic frame sampling.
4. Transform frames.
5. Run inference.
6. Store embeddings.
7. Record metadata.
8. Release GPU memory appropriately.

Inference should be performed without gradient computation.

Conceptually:

```python
with inference_mode():
    embedding = encoder(image)
```

No gradients.

No optimizer.

No training.

---

# M2.8 — Embedding cache

This is an important engineering decision.

Do **not** do:

```text
Training experiment
    ↓
load frame
    ↓
run DINOv2
    ↓
GRU
    ↓
repeat 1000 times
```

Instead:

```text
Raw frames
     ↓
DINOv2
     ↓
CACHE
     ↓
┌────────────┬────────────┬────────────┐
│ Experiment │ Experiment │ Experiment │
│     A      │     B      │     C      │
└────────────┴────────────┴────────────┘
```

Once embeddings exist, M3/M4 experiments operate almost entirely on numerical tensors.

That makes experimentation much faster and reproducible.

---

Do not save only:


You need to know what generated it.

I'd store metadata such as:

```json
  "encoder_version": "...",
  "embedding_dimension": 768,
  "preprocessing_version": "v1",
  "sampling_strategy": "uniform",
  "created_at": "..."
}
```

The exact metadata fields can evolve after we know the chosen encoder.

# M2.11 — Representation sanity check

Now we start doing research.

Take two adjacent frames:

\[
E_t,\ E_{t+1}
\]

Calculate cosine similarity:

\[
S_t =
\frac{E_t \cdot E_{t+1}}
{\|E_t\|\|E_{t+1}\|}
\]

For a sequence:

```text
F1 → F2 → F3 → F4 → F5
```

we get:

```text
S1 = similarity(F1,F2)
S2 = similarity(F2,F3)
S3 = similarity(F3,F4)
S4 = similarity(F4,F5)
```

Then plot:

```text
Similarity
1.0 ┤ ●──●
    │
0.9 ┤       ●
    │
0.8 ┤          ●
    │
0.7 ┤
    └────────────────
       1   2   3   4
          transition
```

The assessment specifically asks for temporal embedding analysis and a discussion of how representations evolve over time. Take-Home Assessment

---

# M2.12 — Don't make the common mistake

Suppose we observe:

```text
F1 → F2 similarity = 0.95
F2 → F3 similarity = 0.91
F3 → F4 similarity = 0.55
```

We cannot simply conclude:

> "The model understood that an action occurred at F3."

What we can say is:

> "The visual representation changed substantially between F3 and F4."

Then inspect:

```text
F3
F4
```

and ask what changed visually.

Possible explanations:

```text
object movement
camera movement
scene transition
occlusion
lighting
background change
actual action transition
```

This distinction between **representation change** and **semantic temporal reasoning** is crucial.

> **What does a single visual embedding contain, and what information is potentially only available when multiple embeddings are considered together?**

For example:

```text

scene

      ↓
```

# M2.15 — Preventing another experimental confound

We need to keep the embedding pipeline identical for:

```text
Single-frame baseline
        ↓
Mean-pooling control
        ↓
GRU temporal model
```

For example:

```text
Frames:

F1 F2 F3 F4
 │  │  │  │
 ▼  ▼  ▼  ▼
E1 E2 E3 E4
 │  │  │  │
 ├────┬────┤
 ↓    ↓    ↓
Single Mean GRU
```

The vision representation does not change.

Only the way we combine the observations changes.

That is exactly what we want.

---

# M2.16 — What NOT to do

At this stage, avoid:

### ❌ Fine-tuning DINOv2

Not yet.

### ❌ Testing five different encoders

Not necessary unless the chosen representation clearly fails.

### ❌ Large hyperparameter sweeps

Premature.

### ❌ Building a Transformer, GRU, LSTM and TCN

We haven't reached M3.

### ❌ Optimizing for leaderboard accuracy

Not the objective.

### ❌ Using test data to select the encoder

The test set remains untouched for model-development decisions.

# M2 acceptance criteria

I would use this as our actual engineering gate.

### Pipeline

- [ ] Frozen pretrained visual encoder selected.
- [ ] Preprocessing explicitly defined.
- [ ] Frame sampling explicitly defined.
- [ ] Deterministic validation/test sampling.
- [ ] Embedding extraction works end-to-end.
- [ ] Embeddings cached.

### Data integrity

- [ ] Every embedding maps to a known sequence.
- [ ] Every embedding maps to a specific frame.
- [ ] Frame ordering preserved.
- [ ] Embedding dimensions validated.
- [ ] NaN/Inf/empty embeddings checked.
- [ ] Labels preserved correctly.

### Research analysis

- [ ] Adjacent-frame similarity calculated.
- [ ] Similarity plotted for representative sequences.
- [ ] Embedding trajectories visualized.
- [ ] Numerical changes inspected against actual frames.
- [ ] At least several representative temporal cases documented.

### Reproducibility

- [ ] Encoder/version recorded.
- [ ] Preprocessing recorded.
- [ ] Sampling strategy recorded.
- [ ] Random seeds recorded where applicable.
- [ ] Configuration stored.
- [ ] Exact dataset split inherited from M1.

Once M2 is complete, our system should look like this:

```text
                 ┌──────────────────────┐
                 │    Frozen Dataset   │
                 └──────────┬───────────┘
                            │
                            ▼
                    Frame Sampling
                            │
                            ▼
                    Image Transform
                            │
                            ▼
                 ┌──────────────────────┐
                 │  Frozen DINOv2/     │
                 │  Visual Encoder     │
                 └──────────┬───────────┘
                            │
                            ▼
                    Frame Embeddings
                            │

                            │
             ┌──────────────┴──────────────┐
             │                             │
             ▼                             ▼
      Representation                 M3 Input
         Analysis                       │
             │                          ▼
             │                    Temporal Models
             │
             ▼
       "What changes
        over time?"
```

And **M3 will finally answer the modeling question**:

```text
Single frame
     vs
More frames
     vs
Ordered temporal modeling
```

The important discipline is that **M2 doesn't try to prove H1/H2 yet**. It establishes a trustworthy visual representation and makes sure that when we reach M3/M4, any measured improvement can reasonably be attributed to how we use temporal information rather than a broken or inconsistent input pipeline.

**M2 exit → M3:** once the embedding cache passes validation and the representation analysis is reproducible, we move to **M3 — Baselines & Temporal Model**, where we'll design the exact single-frame, mean-pooling, and GRU architectures and their training/evaluation contracts.
